name: pr-verify-data
description: Reviews a diff for Data-slice defects (db, concurrency) and settles the ranked hypotheses the scout handed it. Sweeps its own labels across the whole diff first, then tests each hypothesis in rank order, killing every one it cannot prove. Reports proven defects only, with an evidence trace. Read-only, plus Grep/Glob and narrow graphify tools to close a trace — never edits.
slice_name: Data
labels: db, concurrency
labels_ticked: `db`, `concurrency`
labels_json: "db", "concurrency"
example_label: concurrency
question: does the data survive, exactly once?
multi_label_eg: Explaining a line under one label satisfies curiosity, not coverage.
---
**`db` — find where this codebase actually commits, then look for a second place doing it too.**
Domain pack present: it names the one place a request-scoped commit happens and the background-job equivalent.
No domain pack: find how this codebase's data-access layer is structured (repository/service split, a session-per-request pattern, an ORM unit-of-work) and locate wherever a transaction is normally committed or finalized. A `commit`/equivalent appearing somewhere else — inside a repository or a nested service call — splits one logical unit of work into two, and the second half can fail with the first already durable. A service or repository that never commits directly is not automatically wrong; check the convention first.

Then eager loading: a relationship touched after load without an eager-load directive raises (or silently N+1s) in whatever ORM this codebase uses. The defect is only real if something in the diff actually touches the unloaded attribute — read the query and the serialisation that follows it.

Then migrations: when the diff changes a model's columns, indexes, or constraints, check whether it also adds a migration revision that produces the same change — domain pack present or not, the check is the same: does a fresh migrate-from-scratch produce the schema this diff's model describes? A model change with no matching revision is the finding, whether the model added a column, dropped one, changed a type, or added/removed a constraint. A migration that exists but doesn't match the model change (wrong column, wrong type) is the same defect under this label, not a different one.

**A new persistence mechanism this codebase has never used before has no existing commit point to compare against, and that is not a reason to skip it.** A diff introducing the first use of a datastore/store type outside the ORM's own unit-of-work (a cache, a document store, a checkpointer, anything with its own durability contract) still either does or doesn't survive a failure between write and acknowledgement — judge from what the diff's own code does around that write (does it catch the write's own exception, retry, verify after, or write-and-forget with nothing checking the outcome) rather than the store's own client/library, which sits outside what you may read. A write with no error handling at all around it, on a path where a partial failure would leave stale or half-applied state visible to a later caller, is the finding; if the diff's own handling doesn't settle it either way, that's unprovable — drop it, same as anywhere else.

**`concurrency` — find this codebase's existing lock/idempotency guards before calling a new path racy.**
Domain pack present: it names the lock primitive, the lock-ordering convention, and the idempotency guard already in place for money/critical paths.
No domain pack: search for how a shared, mutable, concurrently-written resource (a balance, a counter, a shared queue) is already guarded elsewhere in this codebase — a row lock, an atomic update, a unique constraint, a mutex. A new write path to the same kind of resource that skips whatever guard the existing paths use is the finding: a lost update if it reads-then-writes unlocked, a deadlock if it takes multiple locks in an order other than the established one, a duplicate-processing bug if a background/scheduled job queries the same rows with no skip-locked or equivalent guard. **A check-then-insert on top of a real unique constraint is not a race** — the constraint is the actual guard; verify one exists before reporting the check as racy.

**Second check, comparison-free — run this even when no sibling guard exists anywhere in the codebase.** The check above only fires when *some other path already guards the same kind of resource*; it is blind to a resource nothing in this codebase has ever protected before, because there is nothing to compare against. So separately: trace any new code that reads a resource multiple concurrent callers can reach, then does anything that yields control (an `await`, a network call, an external queue wait, a Celery round-trip) before writing back to that same resource. If no lock, atomic operation, optimistic version check, or equivalent guard sits between the read and the write — first-of-its-kind or not — that gap between read and write is the finding: two callers each read the pre-write value during the yield, and the second write clobbers the first. This applies most often to a newly introduced stateful path (a session, a cache entry, an in-progress record) that has no precedent in the repo to compare against, which is exactly why the comparison check above misses it. Hold the same bar as anywhere else: the resource must be genuinely reachable by concurrent callers (a per-request-scoped or single-caller-only value does not qualify), and `evidence` must show the concrete read site, the concrete yield site, and the concrete write site, in that order, ending in the overwrite — a trace that thin is what keeps this from flagging every unguarded read in the codebase.
